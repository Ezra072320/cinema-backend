## 实际运行环境

Windows 本机、16 GB 内存、JDK 21，Docker 中独立启动 MySQL 8、Redis 7.2、Nacos 3.0.3。运行账户、影片、交易、AI 各一个 JVM，网关两个 JVM，共六个应用进程。业务服务使用四个独立 schema 与数据库用户，分别执行 Flyway；通过开启认证的 Nacos 发现服务，使用 OpenFeign 完成真实跨进程调用。

测试数据库、账号、订单均为专门构造的样本，没有连接或迁移用户原有业务数据库。测试进程和专用容器在验证后清理。生产入口、跨机器网络、真实支付平台和外部模型未参与此次联调。

## 双网关共享限流实测

本次通过两个网关直接访问影片列表，**共 1000 次请求，客户端最多 64 个工作线程**，不等同于 1000 个连接同时释放。为观察共享配额，将影片桶临时设为持续 10 次／秒、初始额度 10；测试未经过 Nginx 的 IP 配额。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 1000 |
| 整批耗时 | 2.228 秒 |
| HTTP 200 | 32 |
| HTTP 429 | 968 |
| 其他状态 | 0 |
| 单次 HTTP 请求延迟 P99 | 1.348 秒 |

允许量符合一个共享桶在该时段内的配额，网关副本数没有使配额翻倍。HTTP 状态计数与延迟来自本机测试；它们用于验证准入机制，不用于推算 10 万并发容量。正式 k6 脚本还会检查 HTTP 2xx 响应的 JSON `code=1`，将业务错误计为失败。

## 2026-10-21：本地登录 HTTP 503 修复

实际登录请求曾返回 HTTP 503、`code=3001`、消息“访问人数较多，请稍后重试”。最小复现是使用无效凭据、不携带验证码请求 `/api/admin/login`：正确路径应进入账号服务并返回验证码校验错误，故障时却在网关准入阶段被拒绝。

检查发现 Redis 容器重建后的地址为 `172.19.0.3`，网关持续重连旧地址 `172.19.0.2`；容器 DNS 已更新，Redis 内部 `PING` 正常，各服务口令一致。只重启网关后，就绪状态恢复 UP，同一复现请求进入验证码校验。随后通过入口执行真实验证码生成、管理员登录、携带令牌读取管理员信息，均成功，未输出密码或令牌，也未重置管理员密码。

修复给网关的 Lettuce 客户端设置独立、有生命周期管理的 DNS resolver，将 A/AAAA 与 CNAME 缓存上限设为 5 秒、失败解析缓存设为 1 秒；未关闭限流，Redis 故障时仍返回 503。Lettuce 支持定制地址解析及客户端资源，参见 [官方客户端资源文档](https://github.com/redis/lettuce/wiki/Configuring-Client-resources)。

新增回归测试使用真实 UDP DNS 测试服务：第一次返回 `127.0.0.1`，随后修改为 `127.0.0.2`，记录 TTL 保持 600 秒。原默认缓存行为未在测试窗口内刷新，测试失败；设置缓存上限后通过。限流测试同时验证：额度耗尽返回 429 和“访问人数较多”，Redis 异常返回 503 和“服务暂不可用”。前端同步区分两类响应。

本次完整 Maven `verify` 成功，后端合计 250 项：245 通过、5 项外部数据源测试跳过；前端 8 项测试与生产构建通过。网关、前端 Docker 镜像构建并替换到本地运行环境后，再次通过入口验证验证码、管理员登录及已登录身份查询，均成功；其他业务服务保持运行。记录见本机 `target/login-dns-red.log`、`target/login-dns-verify.log`、`target/login-web-build.log`、`target/login-docker-build.log`。

## 2026-10-21：浏览器登录 CORS 修复

前一次联调未携带浏览器的 `Origin` 请求头，漏掉了浏览器来源校验。补充真实来源后复现：无 Origin 的登录请求可进入验证码校验，`Origin: http://localhost:8088` 与 `http://127.0.0.1:8088` 则返回 HTTP 403、`Invalid CORS request`；5173 来源可通过。网关的 OPTIONS 预检还会返回 403。

根因为后端默认来源仅包含 `http://localhost:5173`，Compose 未传递可调整的来源配置，网关未设置全局预检处理；Nginx 使用 `$host` 转发时还丢失外部端口，使后端无法正确识别同源入口。

修复统一网关与业务服务的 `CORS_ALLOWED_ORIGINS`，本地默认支持 localhost／127.0.0.1 的 5173 和 8088，Compose 中默认来源跟随 `WEB_PORT`。显式配置生产来源时替换本地默认值。网关处理 `/api/**` 的预检，保留 Host，并去重网关／后端可能重复的 CORS 响应头；Nginx 用 `$http_host` 保留外部端口。未关闭 CORS 校验，未授权跨域来源仍被拒绝。

端到端响应头校验还发现，当前 Java `RouteLocator` 路由不会继承 YAML 路由的 `default-filters`，因此仅配置默认响应头去重仍会产生两份允许来源／凭据头。已将去重、Host 保留及 12 MB 请求体上限直接装配到全部五条 Java 路由；移除未生效的默认过滤器配置。新增实际构建全部路由并执行其过滤器链的回归，确认每条路由都去重响应头、保留 Host，并在请求超限时返回 413 且不调用上游。

新增网关与 Servlet 各 6 项 CORS 回归，加 2 项实际路由过滤器回归。完整后端 `verify` 合计 264 项：259 通过、5 项外部数据源测试跳过，0 失败／错误。Compose 自定义 WEB_PORT 及显式白名单解析检查通过。记录见本机 `target/browser-cors-red.log`、`target/browser-cors-routes-red.log`、`target/browser-cors-final-verify.log`、`target/browser-cors-docker-build.log`、`target/browser-cors-final-docker-build.log`。

更新本地业务服务来源配置、网关及前端镜像后，再次通过 Nginx 入口执行四个来源的真实验证码、管理员登录和已登录身份查询，均成功；实际响应没有重复的允许来源／凭据头。四个来源的跨域 OPTIONS 预检返回 200，并正确允许 POST、Content-Type、Authorization、Idempotency-Key；未授权来源的 POST／OPTIONS 均返回 403。Nginx 配置检查通过，所有业务服务和网关就绪。验证未输出密码或令牌。
