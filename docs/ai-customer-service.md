# AI 客服用户业务升级

范围为 cinema-web / cinema-server 已有的单影院用户业务，保留 Spring AI、Qwen 配置和 MySQL 会话历史。

## 2026-10-22 本地微服务联调

本轮验收已完成，详细结果、复现命令和截图见 [本地验收记录](local-ai-acceptance-2026-10-22.md)。

本节更新下文旧版的流结束、工具上下文和停止行为。运行方式为单套 MySQL、Redis、Nacos，以及各一份 gateway、identity、catalog、trade、ai、web；云服务器的扩容和故障演练另行进行。

- 每次工具调用的名称、参数和返回结果以 `tool_context` 消息保存在 AI 库，最近窗口按原有 24000 字符预算裁剪；每轮工具记录另限约 9000 字符，单个返回最多 4000 字符并标记截断。记录不出现在用户消息列表中，不改变现有数据库结构。下一轮仅用它找影片、场次、座位、订单编号，再用领域服务核对最新状态，不把历史库存或支付状态当当前事实。
- 正常文本仍为 JSON 字符串帧，错误仍为 `type=error` 对象。新增 `type=done` 对象：`{"type":"done","completed":true,"actions":[...]}`。历史、拟单补救和生成占用先收尾，再发送数据库真实服务单快照；模型失败也返回 `completed=false` 和已经生成的服务单。前端直接接收该快照，流异常时再查询列表。未收到 done 就断连会显示中断，不再误判回复完整。
- 新增 `POST /api/ai/stop/{chatId}`，只允许会话本人停止。前端先中断传输并请求服务端结束本轮，再开放输入；切换/新建对话同样停止原生成。停止不等于撤销已生成的服务单，不确认就不会办理业务。
- 中断或模型失败的历史会写入明确标记，即使首个 token 尚未返回也记录停止结果，避免下一轮模型把已停止的问题当作未答事项自动续答。
- 显式提供另一订单 ID 时不再自动替换成会话旧订单；长业务订单号不会被截成短 ID。否定和规则咨询不触发自动售后拟单。购票补单只针对明确购买请求及本轮重新核对的座位，取消或失败收尾不额外补购票单。
- 明确要求提交评价且同时给出一个订单 ID、单一评分和带引号的评论原文时，服务端先实时校验该订单并拟评价单；否定、多个订单或评分、缺少评论原文的请求不自动猜测。普通自然语言仍可通过评价工具拟单，实际提交始终需要用户点击确认。
- 明确场次与一个座号的购买请求先由服务端按真实座位图定位票号、补齐情侣对，并复用票价/可售规则预拟单。撤销的旧确认单不阻止再次拟新单；未明确场次或有多个候选座位时仍先澄清或调用工具，不自动猜座位。
- 前端保留 URL 中的 `chat`，刷新或从支付页返回时可恢复指定会话；多张服务单继续按真实 ID 展示。已办理/撤销/过期卡片不会被晚到的 PENDING 响应恢复成待确认。历史与服务单分别加载，历史失败时明确提供重试并暂时阻止续问。

## 业务地图

| 业务 | 实时能力 | 办理与页面 |
| --- | --- | --- |
| 选片 | 片名、别名、类型、导演、演员搜索；按评分推荐；全国票房/本店销售榜 | `/movie/{id}` 的详情、演职、图片和预告片 |
| 影厅排期 | 类型、容量；日期、影片、影厅、时间段、单张预算筛选；分页、余票 | `/hall`、`/hall/{movieId}` |
| 选座购票 | 可读座号精确定位、票号、座型、实际票价、情侣配对、分页与座型汇总 | 购票确认单，用户点击才锁座下单；`/seats/{scheduleId}` |
| 支付 | 本人待支付订单及支付入口 | `/pay/{orderId}`，用户选择既有模拟支付渠道 |
| 订单售后 | 本人订单按状态/片名/订单号片段分页；详情、座号、退款预估/记录 | 取消/退款先拟确认单；`/order/{id}` |
| 想看 | 本人清单、想看状态、后续排片 | 加入/移除确认单；目标状态相同不反转 |
| 评价 | 影片公开口碑/平均分/分布、本人评价列表、本人订单的可评价状态 | 1–5分与用户评论原文确认单；也可打开原评价页或 `/me/reviews` |
| 账户 | 昵称、年龄、状态、注册时间，不输出密码/openid | 修改昵称/年龄确认单；头像用 `/me/info`，改密用 `/auth/reset` |
| 注册登录与帮助 | 实际步骤、支付时限、座型和退票规则 | 注册、登录、改密页面与门户退出入口 |

本店有未开场场次和大陆市场在映分别处理，不把第一页数量当作全天总数。预计散场根据影片时长计算，不把含清场的排片结束时间当散场。

原示例知识库的积分、优惠券、生日券、会员余额、电子发票、免费饮品等没有业务实现，已移除相应承诺。项目支付、退款为模拟业务；客服不承诺真实扣款/到账、检票核销或在线人工转接。

## 真实服务单

模型工具只能拟单，不能执行确认。服务单显示影片/订单、场次、座号、真实票价/退款金额、评论原文等明细，有效期5分钟。点击页面“确认办理”才会调用既有领域服务；聊天里说“确认”不能绕过该入口。

确认时重查业务数据，金额或明细变化时拒绝旧确认单。退款预估和实际退款共用 `OrderRefundPolicy`，订单域另检查已确认的预期金额，避免跨档执行。情侣座须整对，最多6张实体票，使用实际 `ticket.price`。

确认通过数据库行锁和同一事务保证幂等；重复点击返回已办理结果。失败回滚，用户可重查或撤销。确认单与结果持久化，历史会话可回看。页面只展示真实数据库服务单，模型文字和虚构链接不能触发业务。

## 工具与身份

共22个明确工具：

- 查询：`searchMovies`、`movieDetails`、`movieRanking`、`movieReviews`、`listSchedules`、`listHalls`、`availableSeats`、`seatDetails`、`myOrders`、`orderDetails`、`myProfile`、`myWantList`、`myReviews`、`myServiceRequests`。
- 拟单：`prepareBooking`、`prepareBookingBySeat`、`prepareOrderAfterSale`、`prepareCancellation`、`prepareRefund`、`prepareWant`、`prepareReview`、`prepareProfile`。

使用具体 `ToolResult` 返回类型；Spring AI 1.0 会忽略直接返回 Object 的注解方法，测试覆盖全部工具注册。拟单采用独立扁平参数工具，减少模型漏调用和复杂嵌套命令填错。

### 座号精确查询与购票（2026-10-21 修复）

**症状**：用户明确说“场次ID为1的2排2座”时，客服可能回答别的座位不可售，或把“2排2座”买成“2排3座”；有票的 VIP/情侣座被误判为不可购买。

**根因**：旧 `availableSeats` 只能按页罗列（每页40张），并带一个可选的 `seatType` 过滤；模型既不能按显示座号精确定位，又会误填座型筛选，还会在分页结果里“挑一个最接近的”座位。另有两处一致性隐患：票价来自第二次票查询，两次快照之间可能不一致；情侣座只要单张票可售就被列为可买，确认时却因另一半已售失败。

**修复**：

- 新增 `seatDetails(scheduleId, seatLabel)`：把“2排2座/第2排第2座/2-2”归一成 `2-2`，精确定位该场次该座号，返回真实状态、票价、`ticketId`、情侣对信息；找不到座号时明确要求核对，不推测已售。
- `availableSeats` 增加可选 `seatLabel`，取消模型侧的 `seatType` 过滤；返回 `totalPages/hasMore/typeSummary/reason`，翻页不再把第一页当全部。
- 座位图的 `SeatItem` 直接下发 `price`，AI 不再单独查一次票；情侣座只有两半都可售才计入可售，并给出 `pairedTicketIds`。
- 新增 `prepareBookingBySeat(scheduleId, seatLabel)`：用户点名座号并明确说“帮我买/就买”时，一次完成精确查询和拟单，避免模型在“查到可售”后反复索要口头确认。
- 交易服务新增内部评价查询接口，AI 增加 `movieReviews`（按片名解析、校验 movieId、返回平均分/分布/脱敏评价）和 `myReviews`（本人评价分页）。

**取舍**：精确座号以选座页显示标签为唯一口径；座号不存在时宁可请用户核对，也不做模糊猜测。情侣对两个物理座位共用一个显示座号但有两张票，工具同时返回两个 `ticketId`，由页面服务单展示“共2张实体票”后由用户确认。服务单仍不锁座、不扣款，聊天中的“确认”不能绕过页面确认。

### 支付状态与多服务单（2026-10-21 修复）

**症状**：用户支付后追问，客服仍说订单“待支付”；用户要求退款时客服口头说“已生成退票服务单”，但页面没有第二张服务单；再追问时客服回答“订单不存在”。

**根因**：

- 多轮上下文只回放 user/assistant 文本，不回放工具结果。订单 ID 只存在于上一轮工具返回中，下一轮模型不知道 `/pay/4` 代表订单 4，容易用猜的 ID 查询/退款。
- 模型把“服务单 DONE”误当成“订单已支付”，没有调用 `orderDetails/myOrders` 现查订单表状态。
- 取消和退票是两个独立工具，模型需要自己先判断状态再选工具；状态判断错或 ID 猜错时，工具返回失败，模型却继续宣称“已生成”，实际没有 `ai_action` 落库，页面自然不显示。
- 服务单去重只对“同 payload 且仍 PENDING”的动作生效，不是“一个会话只能生成一张”；真正原因是第二张根本没有创建。

**修复**：

- 新增 `prepareOrderAfterSale(orderId)`：服务端先 `orders.detail` 现查状态，待支付自动生成取消单、已支付按退票规则自动生成退票单；已退款/已关闭直接说明，不重复拟单。模型不再需要自己判断该用取消还是退票。
- 每轮系统提示注入“本会话最近服务单”上下文（类型、服务单状态、`orderId`、path、标题），订单 ID 从 `/pay/{id}`、`/order/{id}` 提取；上下文明确标注“服务单状态 ≠ 订单支付状态”。
- 提示词明确：支付状态必须 `orderDetails/myOrders` 现查；`DONE` 只代表订单已创建/服务单已执行；取消/退票优先用 `prepareOrderAfterSale`；没有 `action.id` 不得宣称生成成功；同一会话允许多张服务单。
- `CREATE_ORDER` 仍 PENDING 且没有 `orderId` 时，提示模型让用户点击该服务单的“撤销”，而不是生成取消订单。

**前端多服务单**：会话底部按数据库返回的全部服务单渲染，不再只展示一张。待确认排在前面，已办理/过期保留；头部显示服务单总数和待确认数，点击可跳到服务单区域；支持“全部／待确认”筛选。每次回复结束（包括流式中断）都重新拉取 `/api/ai/actions/{chatId}`，后端在模型调用前预生成的第二张服务单不会因为流式失败而漏显示。服务单接口返回 `Cache-Control: no-store`；前端用请求序号丢弃晚到的旧响应，避免旧列表覆盖新列表。

**购票补单（2026-10-21 补充）**：`seatDetails` 或带 `seatLabel` 的 `availableSeats` 在确认可售时会记录本会话最近的座位（scheduleId + 两个/一个 ticketId，10 分钟有效）。如果模型回复声称“已生成购票服务单”但实际没有落库，流结束时会按该座位补一张待确认服务单；用户下一条说“没看见/没有生成/还是没有”，且上一条回复确实声称购票成功时，也会在模型调用前按最近座位补单。退票文案不会被误判成购票补单。

**为什么仍可能“看不到”**：

- 模型只说了“已生成服务单”，实际没有调用任何 `prepare*` 工具，数据库没有新行。购票/取消/退票已有确定性补单；其他操作（想看/评价/资料）仍依赖模型调用工具。页面不伪造卡片，会显示“未检测到新的服务单记录”警告，并提供刷新/重发入口。
- 用户在工具写入前点击“停止回复”，动作可能晚几百毫秒才落库；停止后会延迟再刷新一次。
- 多张卡片位于长消息下方，可能被滚出视口；头部“服务单 N”按钮可直接定位，新增服务单也会自动滚到服务单区域。
- 服务单按 `chatId` 隔离：新建会话后旧会话的服务单不会出现在新会话，需要从左侧会话列表切回原会话。
- 同一订单、同一操作类型且仍 PENDING 的重复请求会复用同一张（幂等），不会生成第二张一模一样的卡片。

**取舍**：上下文只带最近 10 条服务单的类型/状态/ID/路径，不带完整 summary，控制 token 且避免把用户资料重复喂给模型；订单支付状态始终不缓存，以交易服务实时查询为准。多张服务单仍由页面按数据库真实记录渲染，模型文字不能替代。

`/api/ai/**` 仅允许 USER。`AiIdentity` 经每请求的 ToolContext 注入，不依赖 Reactor 线程的 ThreadLocal；userId/chatId不属于模型参数。先检查会话归属再读上下文，订单/服务单同样校验归属，SQL参数绑定并限制分页。

保留MySQL历史，最近20条且在24000字符预算内进入上下文（超出从最旧丢弃）；本实例同会话同时只接受一条生成请求，且每用户并行生成 ≤2、每日 ≤200 次。SSE帧契约**有意分叉**：正常 token 帧是 JSON 字符串字面量（如 `"你\n好"`），错误帧是裸对象 `{"type":"error","message":"…"}`；前端 `decodeAiEvent` 对二者都兼容（string→文本、object.type=error→错误帧），不把错误帧统一成字符串字面量是为了保住前端的错误高亮与重试入口——若日后要统一需先同步改前端。建立流之前的参数/权限错误返回JSON和HTTP错误状态。前端标注中断、支持停止、切换、重试、会话删除。

本地业务指南完整加入系统上下文，不再依赖远程嵌入初始化或检索命中；移除记录完整提示词的默认日志advisor。Markdown经DOMPurify处理，只保留已实现用户端路由，不加载模型提供的远程资源。

附带修复：修改昵称后 `/user/info` 按JWT不可变ID读取，防止旧昵称被复用时取错资料；评价页不再多传后端不接受的movieId字段。
